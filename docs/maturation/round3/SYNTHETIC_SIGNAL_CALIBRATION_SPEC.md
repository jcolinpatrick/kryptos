**Status:** Pre-launch. Criteria locked before any synthetic CT is constructed or any controller cycle is run.
**Authored:** 2026-04-25
**Doctrine:** `feedback_preregister_thresholds.md` + `feedback_two_tier_preregistration.md`. This document is the binding criterion set; the postmortem will judge against THIS file's criteria, not against post-hoc relaxations.
**Companion:** `K4_STRATEGIC_RECONSIDERATION.md` §2-§3 (the question this exercise informs but does not answer).

---

## 0. Why this exists

Five consecutive K4 campaigns (v1, v2, v3, A, B+verification, C-attempt-2) have produced zero signal-level alerts. The strategic question — *would more cycles, e.g. a month-long unattended run, find K4* — depends on whether the bottleneck is:

- **(a) Cycle count** (the candidate generator proposes the right family eventually; given enough cycles the DSL exhausts to it), in which case scale is the right axis, or
- **(b) Candidate generator proposal-distribution width** (the prompt + anchors + corpora bound what candidate generator proposes; the right family is or isn't in that distribution), in which case scale doesn't help.

This exercise produces a calibration: under a *known* synthetic CT whose mechanism IS in the proposal distribution, does the architecture find signal at scale N? If yes, "month-long run = ~30N" gives an honest expected-coverage number for real K4 if it's also in the distribution. If no, scale isn't the lever and §2/§3 of the strategic doc need a different answer.

The exercise is **not** a search for K4. The exercise is a calibration of the search architecture against a known answer.

## 1. Goal and falsifiable predictions

### 1.1 Primary tier (Test 1 — Baseline, thematic in-pool keyword, no elim history)

**Setup:** Synthetic CT generated by Quagmire III on KRYPTOS-mixed alphabet with keyword **`SERPENTINE`** (`wordlists/thematic_keywords_v2.txt` slot 213; verified absent from both Oranchak pools and from prior Quagmire-keyword elimination history on real K4 — the project's serpentine eliminations were against transposition families, not against SERPENTINE-as-keyword). Synthetic plaintext is English text constructed to contain `EASTNORTHEAST` at positions 21-33 and `BERLINCLOCK` at positions 63-73 verbatim, so all kernel asserts (CRIB_DICT, SELF_ENCRYPTING) hold without modification.

**Why this keyword:** SERPENTINE is thematically grounded (the sculpture itself has a serpentine form; the word is in the thematic_v2 corpus the controller surfaces for QIII candidates) and carries no elim-history baggage as a Quagmire keyword. Cycles-to-signal therefore measures the architecture's *pure* search speed against a representative K4-shape candidate, uncontaminated by elimination-broadcast effects (those are tested separately in T2). Per `feedback_k4_keywords_must_fit_public_art_context.md`, SERPENTINE fits the puzzle's physical/structural language frame.

**Predictions (locked):**

- **PASS:** the controller fires at least one SIGNAL-level alert (`crib_score >= 18 AND bean_passed AND ngram_per_char >= -4.0 AND p_value_vs_null <= 1e-6`) on the synthetic CT within **30 cycles**.
- **FAIL:** no SIGNAL-level alert by cycle **60** (extension allowed once if cycle 30 shows non-trivial parameter exploration in progress; second extension forbidden).
- **INCONCLUSIVE:** infrastructure failure (controller halt for non-research reason, fatal kernel error, etc.) in <30 completed cycles. Re-run after fix; do not pool with new attempt.

**What PASS means:** the architecture *can* find signal on its own worked example, given enough cycles. Calibration: report `cycles_to_signal_T1 = N`. Then "month-long run buys ~30N coverage" becomes the operative scaling claim.

**What FAIL means:** the architecture cannot find signal even when (a) the mechanism is fully DSL-supported, (b) the keyword is in the thematic_v2 corpus the controller surfaces, (c) the cribs match, (d) the cipher family is in K1/K2 lineage, and (e) no elim-history filter applies. This is strong evidence that adding cycle count to real K4 won't help. §2 of the strategic reconsideration would gain a hard data point.

### 1.2 Secondary tier (Test 2 — Elimination-scoping test)

**Setup:** Identical to Test 1 except the keyword is **`DEFECTOR`** (`wordlists/thematic_keywords_v2.txt` slot 119). Same Quagmire III + KRYPTOS alphabet, same synthetic-PT crib construction, same scoring gates.

**Why this keyword:** DEFECTOR is the strongest-prior thematic Quagmire-keyword candidate the project has tested on real K4 — it hit a 15/24 ceiling and is on the briefing's DO NOT TEST list ("DEFECTOR/PALIMPSEST as keywords, 15/24 ceiling exhaustively confirmed"). On a *synthetic* CT generated by Quagmire III + DEFECTOR, the elimination history does not apply (different CT, different mechanism instance). T2 therefore tests an architectural correctness property: *does the system correctly scope its elimination history to the specific (CT, mechanism) pair, or does it broadcast?*

**Predictions (locked, three meaningful outcomes):**

- **PASS:** SIGNAL-level alert by cycle 100. Interpretation: elimination scoping works correctly. The architecture treats real-K4-CT and synthetic-CT as distinct objects. Calibration: report `cycles_to_signal_T2 = N` for a high-prior keyword.
- **FAIL — cycle exhaustion:** candidate generator proposes DEFECTOR (verifiable in the theory ledger), the DSL dispatches it, but no SIGNAL fires by cycle 100. Interpretation: standard cycles-to-signal miss. Compare against T1's cycles-to-signal for the no-elim-history case — if T2 takes meaningfully longer than T1 on a higher-prior keyword, that itself is a data point.
- **FAIL — early rejection (architectural finding):** candidate generator proposes DEFECTOR but adversarial-review, critic, or controller short-circuits the dispatch citing real-K4 elimination history (do-not-revive list, DEFECTOR=15/24 prior, similar). Detected via grep of red-team verdicts and CRITICIZED-stage theory ledger entries for "DEFECTOR" + elimination-language tokens. Interpretation: **architectural bug — elimination logic broadcasts beyond its established (CT, mechanism) scope**. T2 "fails" but the finding justifies a controller fix and is itself the most valuable outcome from a Purpose-B perspective.

**Test 2 is exploratory** per `feedback_two_tier_preregistration.md`. It does not contribute to the primary calibration claim. It tests an architectural correctness property independently.

**Test 2 only runs if Test 1 PASSes.** If Test 1 fails on a no-elim-history keyword, T2 with elim-history is moot.

### 1.3 What this calibration does NOT measure

- **Whether K4's mechanism is in the proposal distribution.** Synthetic-pass tells us the architecture *can* find Quagmire-III-with-pool-keyword at scale N; it tells us nothing about whether K4 is Quagmire III, has a pool keyword, or has any property that maps to this calibration.
- **Whether the proposal distribution would *eventually* widen.** A 60-cycle and 100-cycle horizon doesn't measure asymptotic candidate generator behavior; it measures behavior at the scales we've actually run before.
- **Whether the architecture's null-baseline classifier is correctly calibrated for synthetic CTs.** The matched-family null cache is computed against real K4. For synthetic CTs of the same length (97), it's approximately correct; we accept this approximation for the calibration.

## 2. Build plan

### 2.1 File changes

| File | Change | LoC est. |
|---|---|---|
| `src/kryptos/kernel/constants.py` | Add `KRYPTOS_CT_OVERRIDE` env-var read at top of module. If set, replace `CT` with the override; print stderr warning; gate K4-specific assertions in `_verify()` behind a `_SYNTHETIC_MODE` flag. | `scripts/_infra/synth_signal/build_synthetic.py` (new) | CLI that takes `(mechanism, keyword, test_id)`, constructs a synthetic English plaintext containing the K4 cribs at canonical positions, encrypts under the chosen mechanism, writes `synth_signal/<test_id>/{synthetic_ct.txt, synthetic_pt.txt, manifest.json}` | ~120 lines |
| `scripts/_infra/synth_signal/launch.py` (new) | Thin wrapper: sets `KRYPTOS_CT_OVERRIDE` from manifest, points internalcontroller at fresh `db/synth_<test_id>_<timestamp>.sqlite`, invokes the same controller code path. | `tests/test_synthetic_mode.py` (new) | (1) Verifies override path produces correct synthetic Bean derivations from a known synthetic example; (2) verifies that without override set, all real-K4 constants and tests pass unchanged; (3) verifies the taint sentinel is written and detectable. | ~80 lines |
| `<internal>/SYNTHETIC_SIGNAL_CALIBRATION_SPEC.md` | This file. | — |

**No changes to <internal>/ controller code.** The architecture is supposed to behave identically; we're feeding it a different CT through a clean override path.

### 2.2 Build order and gates

1. Write the kernel-constants override + `_verify` gating. Run full test suite (`PYTHONPATH=src pytest tests/`); ALL existing tests must still pass with override unset. **Hard gate: any pre-existing test that breaks blocks the build.**
2. Write `tests/test_synthetic_mode.py` and verify the override path actually swaps CT and re-derives Bean correctly against a hand-checked example. **Hard gate: new tests must pass.**
3. Run internal's `self_test.py` (`PYTHONPATH=src python3 <internal> --panel all --mode dry-run`) — must still rediscover K1/K2. **Hard gate: self-test failure blocks the build.**
4. Write `build_synthetic.py`, generate T1's synthetic bundle (Quagmire III + KRYPTOS alphabet + keyword `SERPENTINE`, synthetic English PT containing the canonical cribs at 21-33 and 63-73). Verify the synthetic CT decrypts to the synthetic PT round-trip; verify Bean derivation produces a non-degenerate constraint set on the synthetic. Inspect by hand before launch.
5. Write `launch.py`. Dry-run mode tested first; verify env-var propagates, sentinel file lands, fresh DB is used.
6. Pause for operator (Colin) sign-off before launching Test 1.

### 2.3 Anti-overfitting and contamination safeguards

- **Synthetic results never enter the real K4 ledger.** Fresh DB per test; sentinel file alongside; sentinel asserted by launcher before any cycle dispatches.
- **The override is environment-scoped, not module-scoped.** A pytest run in a separate shell sees real K4 unless explicitly opted in. No risk of contaminating CI or local test runs.
- **The synthetic plaintext does not contain the keyword in cleartext.** The keyword is the cipher key, not text content. The plaintext is mundane English padded around the canonical cribs.
- **The synthetic plaintext does not contain unusually high-quadgram phrases beyond the cribs.** Construction guideline: pick padding text from a corpus of plain English at neutral quadgram per char (around -2.5 to -3.0). Verify at build time.
- **The candidate generator prompt is unchanged.** The architecture sees the synthetic CT through the same pipeline that sees real K4. We are not "telling" the controller this is synthetic; if it can't tell, the calibration is honest.
- **Keyword corpora are unchanged.** Both T1 keyword (`SERPENTINE`, thematic_v2 slot 213, no Quagmire-keyword elim history) and T2 keyword (`DEFECTOR`, thematic_v2 slot 119, has 15/24-on-real-K4 elim history) are pre-verified against the same corpora the controller actually consults.

## 3. Run plan

### 3.1 Wall time and resource estimates

| Phase | Wall time | Compute | Tokens |
|---|---|---|---|
| Build (file changes + tests) | ~1 day | Local CPU | 0 (no API) |
| Test 1 launch + run (worst case 60 cycles) | ~6-10 hours | 28-core local | Per-cycle candidate generator + critic + red-team + stat-audit (matches Campaign A/B/C envelope) |
| Test 1 postmortem | ~1 hour | — | 0 |
| Test 2 launch + run (only if T1 PASSes; up to 100 cycles) | ~10-16 hours | 28-core local | Same envelope |
| Final postmortem + decision update | ~2 hours | — | 0 |

**Total: 2-3 days end-to-end** (all within a single Claude session window; no compute capacity concern per `feedback_do_not_cap_runtime.md`).

### 3.2 Halt conditions

- **T1 cycle ≥ 60 with no signal:** declare FAIL, do not run T2, write postmortem.
- **T1 SIGNAL fires:** record `cycles_to_signal_T1`, decide whether to run T2 (yes if PASS criteria met cleanly; no if signal fired at exactly cycle 60 with thin margin — flag for review).
- **T2 cycle ≥ 100:** declare outcome (PASS or FAIL based on whether SIGNAL fired); write postmortem.
- **Any infrastructure failure** (controller crash, kernel exception, DB corruption, env-var not propagated, sentinel file missing): halt, postmortem the failure, do not retry without root cause + fix.
- **Operator-initiated halt:** Colin can call halt at any cycle. Postmortem records cycle count and observed state.

### 3.3 Postmortem template

The Test 1 and Test 2 postmortems both populate (separately):

- Outcome: PASS / FAIL / INCONCLUSIVE per locked criteria
- `cycles_to_signal` (if PASS) or `cycles_at_halt` (if FAIL)
- DSL kind distribution across the run (compare to Campaign A/B/C)
- Whether quagmire was dispatched at all, and how many times
- Whether the keyword (`SERPENTINE` for T1, `DEFECTOR` for T2) was attempted, and (for T2) whether early-rejection language appears in any red-team / critic / controller log entry that mentions DEFECTOR
- Candidate generator parse success rate, fallback rate, halt counters (matches Campaign A criterion 5)
- Any prompt-bug or DSL-coverage anomalies surfaced
- One-paragraph interpretation against the strategic-doc questions in §2 (does this update Purpose A vs B?) and §3 (does this update stop-conditions?)

## 4. Decision matrix (post-Test outcomes)

This is what the calibration *means* in operational terms. Locked before launch so post-hoc rationalization is constrained.

| T1 result | T2 result | Operative interpretation |
|---|---|---|
| PASS in N≤30 | PASS | Architecture finds signal at scale on a no-elim-history thematic keyword AND correctly scopes elimination on a known-eliminated thematic keyword. Both calibration and architectural-correctness data are positive. Month-long run for real K4 is well-motivated *if* K4's mechanism is in the proposal distribution at all. The §1 belief ("search won't find it") is challenged. |
| PASS in N≤30 | FAIL — cycle exhaustion | Architecture finds clean case at scale; high-prior keyword takes longer or doesn't fire by cycle 100. Tells us cycles-to-signal varies with keyword position in surfaced pool — informative for run-length sizing, not an architectural bug. |
| PASS in N≤30 | FAIL — early rejection | **Architectural bug surfaced.** Elimination logic broadcasts beyond (CT, mechanism) scope; the controller refuses to try a keyword on synthetic CT because the same keyword was tested on real K4. Calibration on T1 is still valid; T2 outcome triggers a controller-correctness fix as the next session's work. This is a high-value finding even though T2 "fails." |
| PASS in 30<N≤60 | (T2 may or may not run) | Architecture finds signal but slowly even on the easy case. Month-long buys ~30N where N is large; expected-coverage is modest. Cycle expansion has positive but bounded value. |
| FAIL | (T2 not run) | Architecture cannot find signal on its own worked example. Strong evidence that more cycles on real K4 won't help. §1 belief is supported with a hard data point. §2/§3 should pivot toward Purpose B explicitly, or toward primary-source disclosure as the only realistic path. |
| INCONCLUSIVE (infra fail) | n/a | Fix the infra; re-run. Does not update strategic doc until a clean run completes. |

The matrix is binding. If the operator post-hoc wants to relax criteria ("60 cycles isn't really enough, let's go to 120"), that relaxation gets logged as a separate decision and the original outcome is preserved.
